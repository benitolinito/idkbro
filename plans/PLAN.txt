STATUS: Superseded by the co-prompting-only product direction.

MultiCode now shares one host-owned coding-agent session. Participants share prompts, streamed agent activity, approvals, questions, and read-only agent previews. Participant workspaces, Yjs text collaboration, cursor presence, manifest synchronization, and workspace checkpoints are no longer product features.

The material below is retained only as historical design context and must not be treated as the current implementation plan.

Full MultiCode real-time collaboration plan
This is the implementation plan I would use against the current 3008a83 baseline.
The final product will use:
- Real local VS Code workspaces for every user.
- Yjs for Google Docs–style human text collaboration.
- A dedicated host daemon as the authoritative session.
- Git checkpoints for bootstrap and recovery only.
- A separate Codex worktree.
- Near-real-time, read-only Codex previews.
- Short merge-time locks and an all-or-nothing workspace commit.
1. Target experience
Human collaboration
Both users can:
- Open and edit the same files in normal VS Code editors.
- See changes within a few hundred milliseconds.
- See cursors, selections, presence, and active files.
- Create, rename, move, and delete files.
- Use IntelliSense, formatters, debugging, terminals, and other extensions.
- Continue editing while Codex works.
Codex collaboration
Both users can:
- Submit or approve prompts.
- See Codex messages and command output live.
- Follow Codex’s changing files in a read-only diff view.
- Continue editing shared files while Codex works separately.
- See a clean Codex turn merged automatically or sent to conflict review.
Codex changes will be near-real-time file snapshots, not character-by-character model typing.

3. Non-negotiable correctness rules
1. The host session daemon is the only authority for room state.
2. An edit is guaranteed only after the daemon durably records it.
3. Original user checkouts are never modified during collaboration.
4. Codex never writes directly into the collaborative worktree.
5. Codex previews never modify Yjs or shared files.
6. A Codex turn is committed completely or not at all.
7. Locks are enforced by the sequencer, not merely by VS Code UI.
8. A slow participant cannot block the entire prompt queue.
9. The public relay is treated as untrusted.
10. The first release permits only one active or pending Codex turn.
Phase 0: Make the pulled checkpoint system safe
The latest code added valuable Git checkpoint functionality, but the current participant application uses git reset --hard and git clean -fd: [workspace/index.ts (line 197)](/Users/benlin/Documents/idk-bro/packages/workspace/src/index.ts:197).
That is safe for a read-only participant, but it would destroy edits made after joining.
Changes
- Replace in-place participant branch switching with an isolated room worktree.
- Never stash, switch, reset, or clean the participant’s original checkout.
- Make destructive operations legal only inside a validated MultiCode-owned worktree.
- Add a marker file containing the room ID, repository identity, and creation nonce.
- Verify that marker and canonical path before any reset or cleanup.
- Refuse to update a dirty room worktree unless its changes are already acknowledged by the session.
- Preserve abandoned room worktrees until the user explicitly removes them.
Checkpoint role
Keep the existing temporary-index checkpoint creation because it can capture staged, unstaged, and untracked files without modifying the user’s index.
Use Git checkpoints for:
- Initial room creation.
- Late-join bootstrap.
- Crash recovery.
- Periodic compaction.
- Exporting the final room result.
Do not use full Git bundles for live file updates.
Relay corrections
- Stop retaining large source bundles in relay room memory.
- Have a joining client request the current checkpoint from the host daemon.
- Chunk checkpoint transfers instead of sending one 36 MiB JSON message.
- Add per-frame, per-room, and global relay quotas.
- Replace command-completion checkpoints with lightweight preview reconciliation.
- Remove the requirement that every participant acknowledge every checkpoint before the next prompt starts.
Exit gate
- Original participant checkout remains byte-for-byte unchanged.
- Dirty participant room mirrors cannot be silently reset.
- A malicious path cannot cause cleanup outside the room directory.
- Existing checkpoint and relay tests continue passing.

Phase 3: Dedicated session daemon
Create @multicode/session-core and a multicode-session executable.
Responsibilities
The daemon owns:

- Relay connection.
- Participant authentication.
- Operation sequencing.
- Workspace manifest.
- Yjs documents.
- Durable storage.
- Worktree materialization.
- Checkpoint generation.

- Preview state.
- Merge proposals.
- Workspace transactions.
The CLI and VS Code extension become clients of the daemon.
Local IPC
Use:
- Unix domain sockets on macOS/Linux.
- Named pipes on Windows.
- A random local authentication token.
- Token files accessible only to the current OS user.
- Request IDs, subscriptions, cancellation, and heartbeats.
Durable storage
Use SQLite in WAL mode inside the daemon for:
- Sessions.
- Participants and permissions.
- Manifest revisions.
- Document updates.
- Workspace operations.
- Checkpoints.
- Codex turns.
- Pending proposals.
- Workspace commits.
Store large snapshots and blobs in content-addressed files keyed by SHA-256.
A document update is acknowledged only after its SQLite transaction commits.
Crash recovery
On restart:
1. Load the last compacted snapshot.
2. Replay later journal entries.
3. Verify content hashes.
4. Finish or roll back incomplete workspace commits.
5. Reconcile the collaborative worktree.
6. Mark interrupted Codex turns as failed/pending review.
7. Reconnect to the relay using a host resume token.
An agent crash must not close the human collaboration room.

Text edit flow
1. User edits the local VS Code buffer.
2. Extension updates its local Yjs document.
3. Client sends the Yjs update and operation ID.
4. Daemon validates epoch, permissions, limits, and lock state.
5. Daemon commits the update to the journal.
6. Daemon assigns a room sequence.
7. Daemon acknowledges the sender.
8. Daemon broadcasts the update.
9. Other clients apply it to Yjs and their VS Code buffers.
10. Disk projectors save the updated file.
Unacknowledged edits remain speculative. Rejected updates trigger resynchronization.
File operations
Creates, renames, moves, and deletes go through the daemon, not directly through Yjs.
Use compare-and-swap against:
- Manifest revision.
- File ID.
- Document epoch.
- Expected source path.
- Expected content hash where appropriate.
External changes
Watch every room worktree for edits made by:
- Terminal commands.
- Formatters that write directly.
- Build tools.
- Other extensions.
- External editors.
Classify writes using content hashes and materialization generations:
- Known daemon write: ignore.
- Unknown write matching current state: ignore.
- Unknown divergent write: import as a human workspace operation.
- Concurrent divergence: three-way merge or conflict.
Presence

- Cursor position.
- Selection.

- Typing status.
- Follow target.

Phase 7: Live Codex preview
Preview source
The filesystem watcher is the primary source because the current adapter exposes messages and command events but no normalized patch stream: [codex.ts (line 68)](/Users/benlin/Documents/idk-bro/packages/agent-adapters/src/codex.ts:68).

Watcher behavior
- Watch only the agent worktree.
- Exclude .git, dependency directories, caches, outputs, and sensitive paths.
- Debounce for approximately 150–300 ms.
- Read a file only after two stable metadata observations.
- Compute preview changes relative to B.
- Reconcile the entire changed-file set periodically.
- Trigger immediate reconciliation after command completion.
- Detect creates, deletes, and probable renames.
- Hash every preview state.

Phase 8: Optimistic three-way merge
At turn completion:
1. Wait for a short filesystem quiet period.
2. Reconcile the agent worktree.
3. Capture final agent state A.
4. Determine changed set B → A.
5. Capture current human state H₁.
6. Merge B, A, and H₁ outside any lock.
7. Record expected file and manifest revisions from H₁.
Merge cases
Human state	Agent state	Result
Human unchanged	Agent changed	Accept agent change
Human changed	Agent unchanged	Keep human change
Both changed, clean merge	Both	Use merged result
Both changed, conflict	Both	Pending proposal
Agent deletes, human edits	Conflict	Pending proposal
Agent renames, human edits same file	Preserve stable file ID and merge	
Binary changed by both	Conflict	Manual review
File mode changed	Apply only if content merge is otherwise valid	


Use Git rename detection for B → A, but preserve MultiCode stable file IDs.
Phase 9: Short locks and atomic workspace commit
Optimistic lock algorithm
After computing a clean merge:
1. Ask the sequencer to lock the complete changed-file set.
2. Compare current revisions against H₁.
3. If anything changed, release locks and recompute.
4. If they match, queue later updates to affected files.
5. Commit the prepared workspace transaction.
6. Release locks.
7. Replay queued human updates.
Locks include:
- Stable file IDs.
- Source and destination paths for renames.
- Parent paths for creates/deletes.
- Document epochs.
- Expected manifest revision.
The lock should normally last only for the durable commit, not for merge computation or user review.
Logical workspace transaction
Because Yjs transactions are document-scoped, add a transaction above Yjs:
workspace.commit.prepare
workspace.commit.part × N
workspace.commit.finalize
Clients buffer all parts until finalize.
The daemon:
1. Stages all new manifest and document states.
2. Writes one durable workspace-commit journal record.
3. Applies merged text as Yjs transactions against H₁.
4. Updates file records and manifest revision.
5. Broadcasts commit parts.
6. Broadcasts finalize.
7. Materializes the collaborative worktree.
8. Replays queued updates.
9. Resets the agent worktree to the accepted shared state.
Filesystem writes are not physically atomic across multiple files, so crash recovery uses the durable commit journal to finish materialization. User-visible state remains logically atomic.
Queued edits
- Yjs text updates are replayed after the commit.
- Rename updates follow the stable file ID.
- Delete plus queued edit becomes a conflict.
- Epoch mismatch causes client resync.
- No acknowledged human operation is silently discarded.
Phase 10: Conflict proposals
If any file conflicts:
- Apply none of the Codex turn.
- Release locks immediately.
- Preserve B, A, and the conflict metadata.
- Keep the preview available.
- Create a pending proposal.
- Allow humans to continue editing.
Resolution flow
1. Reviewer selects human, agent, merged, or manually edited content.
2. Daemon captures the newest human state H₂.
3. Rebase the resolution against H₂.
4. Reacquire compare-and-swap locks.
5. If the state changed again, retry.
6. Commit through the same workspace transaction mechanism.
Do not apply a resolution calculated against stale human state.
While a proposal is pending:
- Block new Codex turns for the first release.
- Continue human editing.
- Allow discard.
- Allow export as a patch or branch.
Interrupted or failed Codex turns never auto-merge.
